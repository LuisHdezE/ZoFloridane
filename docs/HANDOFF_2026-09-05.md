## Detalles de recuperación que no deben repetirse salvo necesidad

Durante la restauración manual:

- LocalWP MySQL usó el puerto `10004` en esa instancia;
- `DB_HOST` se ajustó a `127.0.0.1:10004`;
- el dump extraído usaba tablas con prefijo `servmask_prefix_`;
- `table_prefix` se ajustó temporalmente a dicho prefijo;
- se normalizaron referencias internas heredadas de `SERVMASK_PREFIX_`;
- se reemplazaron URLs `https://zofloridane.com` → `https://zofloridane-local.local` mediante WP-CLI;
- se creó un administrador local `adminlocal`;
- se reconstruyeron roles/capabilities para recuperar acceso a `/wp-admin`;
- se activó `electro-child`;
- se reactivaron plugins esenciales;
- al activar `zfl-admin`, la Home volvió a verse como el sitio original.

Producción no fue modificada por este proceso.

## Hallazgo arquitectónico principal

La página WordPress configurada como Home tiene ID `10202`, título `home`, `post_content` vacío y plantilla asignada `zfl-home.php`.

El archivo no vive en `electro-child`.

Se comprobó que `zfl-admin` registra/carga dinámicamente la plantilla usando filtros como:

```php
add_filter( 'theme_page_templates', ... );
add_filter( 'template_include', ... );
```

Además intercepta templates para producto y carrito.

Conclusión:

**`zfl-admin` es la pieza principal del storefront personalizado y el lugar natural para implementar gran parte del nuevo UI/UX.**

`electro-child` es muy ligero y actualmente contiene poca lógica.
